## 3. Analysis by group

### 3.1 Happy path (samples 1–11) — mostly healthy

Nine of eleven happy-path cases score above 0.7 on every metric. Two outliers:

**Sample 5 (Hikari, F = 0.54)** — the answer expands into a 5-point numbered checklist covering pool size, slow query log, query performance, indexing, and pool utilization. Faithfulness dropped because RAGAS extracts more atomic claims from a longer answer, and a few reframed points ("appropriate indexes are in place", "make further adjustments as necessary") aren't literal claims in the source. **Not a real quality issue — the answer is correct, just wordy.**

**Sample 6 (DB 100% CPU, CP=CR=0)** — a *real* retrieval failure carried over from v3. The question could match either the Redis thundering-herd thread (ground truth) or the DynamoDB hot-partition thread, and vector similarity picked DynamoDB. The LLM confidently answered from the wrong incident. Root cause: the two threads share vocabulary ("100% CPU", "throttling", "traffic spike"). **Retrieval-layer fix needed.**

**Sample 7 (nginx 504, CP = 0.33)** — the correct thread was retrieved but ranked *third* behind the API Gateway 502 thread and the intermittent 500s thread. Answer is still correct because the LLM used the third chunk. **Ranking issue, not retrieval failure.**

### 3.2 Fallback (sample 12) — behaving correctly, metrics disagree

The assistant correctly refused to answer a topic outside the KB. All four metrics are 0.0, which looks catastrophic but is misleading:

- **Faithfulness = 0** because the fallback text ("I cannot find this information...") doesn't cite context. This is the *desired* behavior.
- **Answer Relevancy = 0** because RAGAS reverse-generates questions from the answer and gets generic KB questions, none of which match the specific Prometheus federation query.
- **Context Precision/Recall = 0** because there's no ground-truth-relevant content in the retrieved chunks — and there couldn't be, since the topic isn't in the KB.

**Interpretation:** these zeros are not a system failure. They highlight that **RAGAS does not have a metric for "appropriate refusal"**. A rubric-based `AspectCritic` metric (available in RAGAS 0.2+) would score this case as a pass. For now, sample 12 should be tracked separately from the aggregate.

### 3.3 Failure-mode probes (samples 13–18)

The six new probes (added after v3) intentionally target LLM generation weaknesses. Results per probe:

**Sample 13 — Parametric Hallucination probe** ("How do I fix a Java OutOfMemoryError?")
- **Faithfulness = 0.27 → probe fired.** The answer includes generic JVM advice ("Increase Memory Allocation", "Profile Memory Usage", "Monitor and Adjust") that isn't in the retrieved context. This confirms the model does leak pretraining knowledge on well-known topics.
- Retrieval also brought back irrelevant RDS + SQS threads (CP = 0.5, CR = 0.67), which likely encouraged the model to generalize.
- **Action:** tighten the system prompt to explicitly forbid generic advice ("If the question is about a general topic not tied to a specific internal incident, do not offer generic solutions — describe only the specific incident from context or return the fallback").

**Sample 14 — Extrapolation probe** ("When will the API Gateway 502 be resolved?")
- **Faithfulness = 1.0 → probe caught nothing (good).** The model correctly said "no specific timeline provided" instead of inventing one.
- **AR = 0.0 is a metric artifact** — the honest "no timeline" answer doesn't semantically match the question's "when will it be resolved" framing, so reverse-question generation fails.

**Sample 15 — Contradiction probe** ("Was the ECS OOM fixed by rolling back the Lambda deployment?")
- **Faithfulness = 0.83 → probe caught nothing.** The model correctly answered "No" and separated the two incidents.
- **CP = 0.33 → retrieval failure.** Only 1 of 3 retrieved chunks was the actual OOM thread; the others were RDS failover and NPE. The model still succeeded because it used the one correct chunk. Confirms the ranking issue seen in sample 7.

**Sample 16 — Query Misinterpretation probe** ("How did we *detect* the SQS DLQ spike?")
- **Faithfulness = 1.0** and **AR = 0.80** — the model gave a coherent answer.
- **CP = 0.0** — RAGAS says *none* of the retrieved chunks help answer "how was it detected", because the thread doesn't describe detection. This is technically correct: the model actually drifted from the question and described the incident instead of saying "detection mechanism isn't recorded". **Mild query-misinterpretation caught.**

**Sample 17 — Incomplete Addressing probe** (4-part Redis herd question)
- **Faithfulness = 0.67, AR = 0.77, CR = 0.75.** The model addressed all four parts, but the fourth ("prevent recurrence across other services") required inference that isn't in the source, dragging faithfulness down. **This is a *feature*, not a bug** — the answer is genuinely useful, and the metric correctly flags the inference.

**Sample 18 — Padding probe** (yes/no answerable IAM question)
- All metrics near-perfect. The model answered in 3 sentences — no padding. **Good behavior confirmed.**

## 4. Findings & recommendations

### High priority

1. **Retrieval ranking is the dominant issue.** Samples 5 (indirectly), 6 (severely), 7, and 15 all show either wrong-thread selection or correct-thread-buried-in-list. Same class of problem across four cases → concrete fix candidates:
   - **Hybrid search (BM25 + vector)** — vocabulary overlap ("100% CPU", "DB", "traffic") is currently the deciding signal on ambiguous queries. BM25 would boost keyword-exact matches for terms like "Redis" or "thundering herd".
   - **Cross-encoder reranker** — cheaper than retraining embeddings; reorders the top-K by finer-grained relevance.
   - **Increase `maxResults` from 3 to 5** — cheap first experiment; if the right chunk is being retrieved but pushed to position 4, the LLM would still see it.

2. **Parametric hallucination is a real risk on well-known topics.** Sample 13 confirms the model happily blends internal context with training data. Tighten the system prompt with an explicit constraint like *"If the question is generic (not tied to a specific incident in the retrieved context), reply with the fallback message. Do not synthesize generic best-practice advice."*

### Medium priority

3. **The Hikari answer style (sample 5) is too verbose for RAG faithfulness.** Consider a system-prompt instruction to *quote or paraphrase, not restructure* the retrieved context. A shorter answer would keep faithfulness at 1.0 without losing accuracy.

4. **Sample 9 (cert expiry, F = 0.71)** adds soft framing ("proactive approach helps ensure...") not present in the source. Same fix as #3.

### Low priority / non-issues

5. **Sample 14 (extrapolation) and sample 12 (fallback) are correctly-behaving cases penalized by RAGAS answer relevancy.** These aren't code problems. Options: (a) migrate to RAGAS 0.2+ and add `AspectCritic` for "appropriate refusal", or (b) exclude fallback-triggering cases from the aggregate and score them separately.

## 5. RAGAS metric artifacts to be aware of

| Situation | What RAGAS does | Why it's misleading |
|---|---|---|
| Honest refusal / "no info" answer | AR ≈ 0 | Reverse-question generation from a non-answer produces generic queries that don't match the specific question |
| Long, well-structured but verbose answer | F drops | More atomic claims are extracted; some are correct paraphrases but not literal quotes from context |
| Complex multi-part question, single-sentence ground truth | AR often drops | Reverse-generated questions match only part of the original multi-clause query |
| Out-of-KB question with retrieved-but-irrelevant chunks | CP/CR = 0 | Correct behavior scores identically to failure |

If we upgrade to RAGAS 0.2+, `AspectCritic` and `NoiseSensitivity` metrics would address several of these.
