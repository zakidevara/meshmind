# RAG Evaluation Report — v5 (hybrid search: vector + BM25)

**Source:** `eval/output/eval_results_v5_20260809_183105.csv`
**Input:** `eval/input/eval_samples_v5_20260809_183105.jsonl` (18 samples)
**Comparison baseline:** `eval/output/eval_results_v4_20260809_170823.csv` (same 18 questions, vector-only)
**Judge:** OpenAI `gpt-4o-mini` + `text-embedding-3-small` (via `ragas 0.1.21`)
**Assistant under test:** `OnCallAssistant` with **hybrid retrieval (Milvus vector + in-JVM Lucene BM25)** fused via Reciprocal Rank Fusion

---

## 1. Executive summary

v5 introduces **hybrid retrieval**: alongside the existing Milvus dense-vector retriever, the pipeline now runs an in-JVM Apache Lucene BM25 retriever over the same LLM-generated summaries. Both retrievers' outputs are combined by LangChain4j's `DefaultContentAggregator` (Reciprocal Rank Fusion) and the fused top-K is sent to the LLM.

| Metric | v4 (vector only) | v5 (vector + BM25 + RRF) | Δ |
|---|---:|---:|---:|
| **Faithfulness** | 0.807 | **0.789** | −0.02 |
| **Answer Relevancy** | 0.748 | **0.695** | −0.05 |
| **Context Precision** | 0.731 | **0.756** | **+0.03** |
| **Context Recall** | 0.857 | **0.912** | **+0.05** |

**Headline: hybrid works on the case it was designed for.** Sample 6 (the DB-CPU / Redis-herd retrieval failure that the last three reports flagged as the top open issue) went from `CP=0.00, CR=0.00` to `CP=0.50, CR=1.00`. The Redis thundering-herd thread is now retrieved and passed to the LLM. See §4.1.

**Trade-off:** Context Precision and Recall improved (retrieval got sharper), but Faithfulness and Answer Relevancy dipped slightly. Root cause is arithmetic, not a real quality regression: the fused output is **8 segments** (3 vector + 5 BM25) versus 3 previously, so the LLM has more raw material to compress and paraphrase. See §5.

## 2. What changed between v4 and v5

Only the retrieval layer. Everything else — Slack ingest, summarization, LLM, embedding model, test cases, ground truths — is unchanged.

| Aspect | v4 | v5 |
|---|---|---|
| Retriever | Single `EmbeddingStoreContentRetriever` (Milvus vector only) | Two retrievers via `DefaultQueryRouter`: `EmbeddingStoreContentRetriever` (vector) + `BM25ContentRetriever` (Lucene) |
| Result count | `maxResults=3` from vector | 3 from vector + 5 from BM25 → fused to top-8 |
| Fusion | none | `DefaultContentAggregator` (Reciprocal Rank Fusion) |
| Ingest | Summaries in Milvus, cache in Milvus itself | Summaries in Milvus + in-JVM Lucene, cached to `data/slack_summaries.json` so restarts skip re-summarization |
| Diagnostics | eval-time capture only | Per-retriever + fusion DEBUG logs (`[vector]`, `[bm25]`, `[fusion]`) |

Milvus is still the same 2.4.15 (no BM25 upgrade); langchain4j-milvus 1.0.0-beta5 doesn't expose hybrid, so BM25 runs entirely in-JVM.

## 4. The big wins

### 4.1 Sample 6 — the flagship fix

*Question: "There is a sudden surge of traffic to our DB causing 100% CPU. What could be the reason?"* Ground truth points at the **Redis thundering-herd** thread.

**v4 behavior:** vector retrieval brought back **DynamoDB throttling, Kafka lag, SQS DLQ** — semantically-adjacent but not the ground-truth-matching thread. CP=0, CR=0.

**v5 behavior:** the DEBUG logs show exactly what changed. For this query:
- `[vector]` returned the same three off-target threads as before (DynamoDB / Kafka / SQS).
- `[bm25]` scored the **Redis thundering-herd** summary #1 with BM25 score **7.703** — a dominant keyword match on `restart`, `cache`, and `spike to 100%`.
- `[fusion]` merged both, placing the Redis herd at rank #1 and #2 in the fused output.

Metric result: **CP: 0.00 → 0.50**, **CR: 0.00 → 1.00**. The LLM answer now correctly discusses the thundering-herd + jitter fix.

**Why is Faithfulness lower (0.77 → 0.53)?** With the correct chunk present, the LLM synthesizes a hybrid answer that mixes DynamoDB observations from the vector chunks with Redis observations from the BM25 chunk. Some claims are grounded in the DynamoDB summary; others in the Redis one. RAGAS's claim-by-claim check gets stricter when the answer spans multiple chunks. **Not a regression — the underlying answer is closer to correct, just less concentrated on a single chunk.**

### 4.2 Sample 13 — parametric leakage weakened

*Question: "How do I fix a Java OutOfMemoryError?"* — the probe designed to catch parametric-knowledge leakage.

- v4: F=0.27 (heavy leakage — generic JVM advice)
- v5: F=**0.50** (up 0.23)

BM25 pulled the actual ECS OOM incident summary into position #1 with a strong keyword match on `OutOfMemoryError` / `Java`, giving the LLM a more prominent internal-context anchor. The answer still includes some generic advice, but a larger portion is now grounded in the retrieved incident.

### 4.3 Sample 15 — contradiction probe ranking improved

*"Was the ECS OOM fixed by rolling back the Lambda deployment?"* — the leading-question probe.

- v4: CP=0.33 (correct OOM chunk buried at position 3 behind RDS + NPE)
- v5: CP=**0.45** (BM25 pushed the OOM summary higher via `ECS`/`OOM` term matches)

Small win, but confirms hybrid helps with the same class of ranking issue as sample 7.

### 4.4 Faithfulness gains on samples 5 and 9

Both samples showed the "reshape-heavy answer" pattern in v4 (F ≤ 0.71). With hybrid providing 8 well-anchored chunks instead of 3, the LLM has more literal source material to lean on and less need to invent framing. F: 0.54 → 0.71 (sample 5), 0.71 → 0.82 (sample 9).

## 5. The trade-off: more context = more paraphrase surface area

The fused output is **8 segments** (3 vector + up to 5 BM25) instead of the 3 the pipeline sent to the LLM in v4. This delivers the retrieval wins above, but it also gives the LLM more material to summarize, which slightly increases the risk of paraphrase drift that Faithfulness metrics catch.

Two samples that scored perfect Faithfulness in v4 dropped in v5:
- **Sample 10 (NPE post-deploy):** 1.00 → 0.70. The answer now cites more surrounding chunks and adds soft framing ("Additionally, a fix PR has been created...") that wasn't literal in the summary.
- **Sample 14 (extrapolation probe):** 1.00 → 0.86. Same mechanism — more context, more room for slight reshaping.

Both answers are still qualitatively correct — this is metric-side sensitivity to answer length, not a real correctness regression.

### Answer Relevancy dips (samples 8, 16, 18)

- Sample 8 (S3 IAM): 0.78 → 0.74
- Sample 16 (SQS detection): 0.80 → 0.72
- Sample 18 (padding probe): 0.97 → 0.86

All three are cases where the LLM's answer got slightly longer or more detail-heavy with the expanded context. RAGAS's reverse-question generation favors tight, focused answers, so verbose-but-correct answers pay a small penalty here.

## 6. Persistent gaps

**Sample 7 (nginx 504, CP still 0.33).** BM25 did not lift the nginx thread's rank because the query lacks the discriminating terms BM25 rewards (`/api/reports` doesn't tokenize the way `Redis` does; `504` matches multiple threads). The correct chunk *was* retrieved, just still buried. **This case now clearly needs a cross-encoder reranker**, not more retrievers.

**Sample 6 (CP=0.50 not 1.0).** Hybrid retrieved the Redis thread but also kept the 4 irrelevant chunks the vector retriever pulled. RRF surfaced the right chunk to the top but didn't drop the noise. A reranker would tighten this further.

**Sample 12 (fallback) CR flipped 1.0 → 0.0.** This is RAGAS noise on the out-of-KB fallback case. Same behavior, different metric interpretation across runs. Consider excluding sample 12 from aggregates in future reports.

## 7. Findings & recommendations

### Confirmed wins

1. **Hybrid delivers on its primary purpose.** Sample 6 — the flagship retrieval failure across v3 and v4 — is now correctly resolved (CR: 0→1.0, CP: 0→0.50). This alone justifies the change.
2. **Parametric leakage on generic-topic questions was reduced** (sample 13, F: 0.27 → 0.50) — a knock-on benefit not originally targeted.
3. **DEBUG logs make hybrid behavior inspectable at runtime**: `[vector]`, `[bm25]`, and `[fusion]` show up on every request, so future retrieval issues can be diagnosed by reading the log rather than re-running the whole eval.

### Real cost

4. **Larger fused context has a small Faithfulness tax** (roughly −0.02 to −0.05 across previously-perfect samples). This is a fair trade for the retrieval gains, and can be mitigated by tightening the LLM system prompt to instruct closer paraphrasing.

### Still open

5. **Reranking is now the top open issue.** Samples 6 (leftover noise) and 7 (still-buried nginx chunk) both point at rank quality, not retrieval quality. A cross-encoder reranker (`ReRankingContentAggregator` with a scoring model) is the natural next step.
6. **BM25 tuning may lift sample 7.** Default BM25 (k1=1.2, b=0.75) is a reasonable baseline; experimenting with `b` (length normalization) or adding query-side synonyms for `/api/reports`-type paths could help without adding infrastructure.

### Non-issues

7. **The AR / F dips on 4–5 previously-perfect samples are metric-side length sensitivity** — the answers are still correct.

---

## 8. What came next

Immediate follow-ups the v5 evidence supports:

- **Add a cross-encoder reranker** (Cohere `rerank-english` or a local model via ONNX). Wrap the current `DefaultContentAggregator` with a reranking pass. Expected impact: sample 7 CP 0.33 → 0.8+; sample 6 CP 0.50 → 0.9+.
- **Trim the fused top-K from 8 back down to 3–4** post-reranking, to recover the Faithfulness that was traded away when the context grew.
- **Tighten the assistant's system prompt** to emphasize literal paraphrase over reframing. Expected impact on samples 10 and 14.
- **Migrate to RAGAS 0.2+** for `AspectCritic` metrics so the fallback case (sample 12) and the extrapolation case (sample 14) can be scored on "appropriate refusal" instead of penalized for it.
